# 阶段 2a 报告：写入监控的诊断模式（ETW）

日期：2026-10-27 到 10-29。设计见 `docs/phase2a-design.md`，决策点 D1–D15 全部按推荐采用。

## 结论

- 2a 完成。以管理员身份运行时，可以开一个 1 到 24 小时的 ETW 诊断会话，记录哪个进程在哪个目录新建、删除、重命名了文件；精确模式还记录写入量和估算增长。数据按"目录 × 进程链 × 小时"存进 `monitor.db`。
- 这些数据接到了增长分析、概览、空间浏览详情和设置里。另有一个无界面的 `monitor` 子命令，用于诊断和验收。
- 默认模式是精确：2a.1 实测满足 D3 的四条，空闲时 CPU 0.07%，工作集增加 22 MB，没有丢失事件。
- **会话一定会停**的几条路都实测过：
  - 到时停止，以及到时停止发生在计时器线程上的情况；
  - 用户停止、关窗口、被外部停止（`logman stop`）；
  - 进程被强制结束后，下次启动或运行 `monitor --cleanup` 时清理，兜底计划任务也会停掉残留会话；
  - 会话停止后计时器线程再读丢失数，原来会出错让进程退出，2a.5 验收时发现并修好。
- 负载核对：用测试负载 WriteLoad 跑默认参数，精确模式下各子目录的新建、删除、重命名个数、写入量、估算增长都和负载报告一致，`EtwSessionTests` 8/8 通过。windows-2022 / 2025 的冒烟测试上，解析器核对 `parse_mismatch=0`。
- 研发方案 1.3 节的目标（见文末"性能目标对照"）：
  - 发布包大小和"监控中 + MFT 扫描"的峰值内存达标；
  - 冷启动 0.1.0 和现在都没达到 ≤ 1 秒，详见那一节。

### 回放：逐项比对和处理速率（2a.2，普通权限）

`EtwBench replay` 把 W2、W3 存下的原始事件送进 `DiskThinner.Monitor` 的 PayloadParser → ReorderBuffer（W = 1 秒）→ MonitorAggregator，单线程回放 5 遍：

| | W2 写入负载 | W3 编译 |
|---|---|---|
| 事件 | 3,519 | 7,426 |
| 处理速率（单线程） | 约 96,000 个 / 秒 | 约 203,000 个 / 秒 |
| 解析失败 | 0 | 0 |

W2 按 WriteLoad 默认参数逐项比对（新建、删除、重命名个数，写入量，估算增长）：small、big、append（含 FILE_APPEND_DATA 的哨兵偏移、重开追加、cmd 的 `>>`）、temp（关闭时删除）、prealloc（只预分配，估算增长 0）、短路径、move（跨目录移动、整个目录改名）共 16 项全部对上。写入进程都是 `DiskThinner.WriteLoad.exe ← cmd.exe`，cmd 的 `>>` 是 `cmd.exe ← DiskThinner.WriteLoad.exe ← cmd.exe`。

回放中修正了两处：快速 I/O 失败后的 IRP 重试要整个跳过（只扣写入量不够，追加写的哨兵偏移会把估算增长算两遍），快速 I/O 的判断只看 IOFlags 为 0（这类事件的 Irp 字段不是 0）；回放要按第一个进程启动事件把相对时间对齐到真实时间，进程表才能按时间找到实例。

抽样阈值 R 取处理速率较低的一个的一半：每秒 48,000 个写事件（设计 5.3 节）。实测里写事件每秒最多 1,938 个，离这个阈值很远。

`monitor.db`（D4）：会话、按小时的统计、目录（按段存）、映像、进程链、`write_stat`（会话 × 小时 × 目录 × 进程链）。设计 5.8 节的最坏情况合成数据（24 小时，每小时一半的行在 500 个锚点上、一半在新目录上，500 种进程链、300 个映像，计数取上限附近的值）：每小时 1,000 行时一天 2.6 MB（目标 ≤ 4 MB），每小时 2,000 行时 4.5 MB（目标 ≤ 8 MB）。保留按开始时间删整个会话，按实际占用的页（不是文件大小）判断，超出上限时只删需要删的那几个。

## ETW 会话和 monitor 子命令（2a.4，2026-10-27）

新增 `DiskThinner.Monitor.Etw`（DiagnosticSession、MonitorRunner、MonitorCleanup）和 `DiskThinner.exe monitor` 子命令。`tools/verify/phase2a-elevated.ps1 -Part accept`（以管理员运行）的结果如下：

| 步骤 | 结果 |
|---|---|
| 2 到时 | `monitor --seconds 30` 退出码 0，`end_reason=timeout`、`session_stopped=true`；正常结束后兜底任务已删 |
| 3 强制结束 | `Stop-Process -Force` 后会话仍在；`monitor --cleanup` 返回 `residual_stopped=1`、`orphans_marked=1`、`task_deleted=1`，之后会话和任务都不在了 |
| 4 兜底任务（D7、V20） | 60 秒的会话开始 10 秒后被强制结束；兜底任务以 SYSTEM 身份运行 logman，在强制结束后 120 秒停掉会话，也就是计划结束后约 1 分钟。会话已经停了但任务还在时，`--cleanup` 会补删任务（`residual_found=0`、`task_deleted=1`）。V20 单独测：`DeleteExpiredTaskAfter=PT0S` 的任务在过期后 54 秒内被系统删除 |
| 5 负载 | 精确和轻量两种模式都加 `--verify-parser`，结果 `parse_mismatch=0`、`lost=0`；CPU 0.26% / 0.24%，工作集约 63–66 MB |
| 7 | 每一步之后都没有 `DiskThinner-Diag-` 会话；默认的 monitor.db 没有被碰（前后都是"不存在"） |

`EtwSessionTests`（`DT_ETW_TESTS=1`、管理员）8 个全部通过。覆盖的内容：开始和停止，停止只执行一次；到时停止发生在计时器线程上，之后能再开始；`logman stop` 后结束原因是 external；残留清理不碰名字不符合的会话；到时停止和并发落盘不交错；用 WriteLoad 小参数和默认参数各跑一次精确模式，逐项比对通过（第 1.3 节第 7 条）；默认参数再跑一次轻量模式，只比对计数。

第一次运行时发现了三个问题，都已修好：

- `--verify-parser` 的差分核对在 TDH 解码出的整数类型和我们的不一致时会抛异常（哨兵偏移会被当成有符号数），导致泵线程以 error 退出。现在改为按位比较，核对里的异常只记一次不一致；报告里加了 `parse_mismatch_first`，会话因为异常停止时 monitor 子命令返回 1。
- 轻量模式不开文件名关键字，看不到关闭时删除（V12）的删除，这和设计一致。测试改为只在精确模式下比对 `temp\` 的删除数。
- 目录改名到一个已经有节点的路径（比如锚点）时，文件状态还挂在旧编号上，之后的写入不再累计估算增长。现在并节点时把文件状态一起换到新编号，补了单元测试。

- 自包含单文件版：3 个文件，exe 109.3 MB，zip 45.8 MB。
- 两个包的文件清单写在 `files-<包>.txt`。

`smoke.ps1`（本机管理员，两个包）0 项失败。单文件版的 `monitor --seconds 15 --mode precise --verify-parser` 收到 48,471 个事件，丢失 0，`parse_mismatch=0`，结束后没有残留会话（V8：单文件版里 TraceEvent 正常工作）。Release 构建没有 NU 警告（V11）。

- 同一次提权运行里，`EtwSessionTests` 8/8 再次通过。

截图检查中发现并修复的问题：

- 工具栏胶囊的圆角外面画成了黑色。原因是直接的父控件背景透明，现在改为取最近的不透明上级的底色。
- 覆盖时段的日期刻度在范围很短时文字重复。现在重叠或文字相同的刻度不再画出。
- 对话框出现了滚动条。原因是嵌套的自动大小面板按换行之前的宽度报首选大小。现在正文固定为内容宽度，排版后再按实际高度加高窗口。
- 表格里"文字 + 标签"那一格的标签压在了文字上。原因是量文字宽度时带了 EndEllipsis 标志，没给宽度时量出来接近 0。
- 范围不到 1 小时时覆盖卡片显示"0 / 0 小时"。现在改按分钟显示。
- **会话停止之后进程崩溃**：每秒的状态计时器在会话停止之后再读 `EventsLost`，TraceEvent 抛出 0x80071069，异常抛到了线程池，进程退出。只有在监控进行中截图并立即关窗口时才碰得到。修法如下：
  - 停止开始之后，`DiagnosticSession.EventsLost` 返回最后一次查到的值，查询失败也不抛异常；
  - `MonitorRunner` 的两个线程池计时器回调整体捕获异常；
  - `EtwSessionTests` 补了停止后读丢失数、停止过程中计时器不出错的断言。

## 性能目标对照（研发方案 1.3 节，设计 1.3 节第 20 条，2026-10-29）

测法：`tools/verify/phase2a-perf.ps1`，比较 0.1.0 和 0.2.0-dev.5 两个发布目录。冷启动是普通权限下交替启动两个依赖运行库版各 5 次（先各启动一次预热，不计）；峰值内存在管理员下由 `phase2a-elevated.ps1 -Part perf` 测。开发机主显示器 150% 缩放。

| 指标 | 目标 | 0.1.0（加 TraceEvent 之前） | 现在 | 是否达标 |
|---|---|---|---|---|
| 冷启动到窗口显示（进程启动到主窗口句柄出现，中位数） | ≤ 1 秒 | 1.35 秒（1.07–3.15） | 1.80 秒（1.28–2.25） | 都没达到 |
| 依赖运行库版发布包 | ≤ 10 MB | 3.2 MB，17 个文件 | 7.3 MB，24 个文件（zip 2.8 MB） | 达标 |
| 监控中（精确）+ MFT 扫描整个 C 盘的峰值内存 | ≤ 300 + 64 MB | 不监控时 322 MB（2a.4 冒烟测试） | 345 MB（111 万个节点，扫描 5.1 秒，监控中收到 27,672 个事件） | 达标 |

冷启动的说明：

- 0.1.0 在这台机器上本来就超过 1 秒。阶段 0 只验证了空窗口能启动，没有按这个口径测过，所以这不是 2a 引入的。
- 现在中位数多了约 0.45 秒，但单次之间差 2 秒以上，抖动比差值大。这一组次数少（按负载约束），区分不了是真实变化还是磁盘缓存和后台负载的影响。
- 主程序 `--report` 里新增的 `traceevent_loaded_at_shown` 确认窗口显示时 TraceEvent 没有加载（设计 5.9.1 节）。新增的启动工作只有 Monitor 和 Monitor.Etw 两个小程序集，以及构造 `MonitorHost`（建两个计时器）。
- 启动后台的残留判定在窗口显示之后才做。
- 冷启动目标在 known-issues 里记一条，阶段 2b 开始前在空闲的机器上按同一口径多测几次，确认是不是 2a 变慢了，不放宽目标。

自包含单文件版 109 MB（zip 45.8 MB），比 0.1.0 多约 4 MB，主要是 TraceEvent。

## 没有在自动验收里覆盖的

- **UAC 交互**：普通权限下点"以管理员身份重启并开始"、在 UAC 里点"否"或点"是"，这一串只覆盖了参数生成和解析（`MonitorUiTests`）。新实例的自动开始用 `--monitor-seconds` 验证过，没有走一遍真实的 UAC 点击。
- **账户不一致**：用另一个管理员账户提权时，新实例不自动开始、打开预填的对话框并显示黄色提示。开发机只有一个账户，这条只由对话框的单元测试覆盖。
- **睡眠唤醒、改系统时间**：由 `SessionDeadline` 的可注入时钟测试覆盖，实机没有测。
- **用电池时兜底任务也运行**：只由 `WatchdogTaskTests` 断言 XML 里的电池设置覆盖。
- **截图缩放**：开发机主显示器是 150% 缩放，截图都是这个缩放；没有 100% 缩放的显示器。
- **讲述人和高对比度**：没有实测，清单见 `docs/known-issues.md`。
