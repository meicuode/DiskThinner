# 阶段 2a 报告：写入监控的诊断模式（ETW）

> 草稿，随子步骤补充。设计见 `docs/phase2a-design.md`。

## 开销实测（2a.1，2026-10-27）

环境：Windows 11 25H2（10.0.26200），22 个逻辑核，NVMe 系统盘；TraceEvent 4.0.0；实测程序 `spikes/EtwBench`，
测试负载 `tests/DiskThinner.WriteLoad`，提权脚本 `tools/verify/phase2a-elevated.ps1 -Part bench` / `bench2`。
所有进程低于正常优先级、一次一个负载；不做人为加压（设计 8.4 节），所以丢失率偏保守。
W1 空闲按负载约束缩短到 3 分钟（设计是 10 分钟），只够看开销的量级。

|---|---|---|---|---|---|---|

编译耗时（`dotnet build src/DiskThinner.App -c Release --no-incremental -m:1`，两轮共 9 次，第二轮按交替顺序）：

| 配置 | 各次（秒） | 中位数 |
|---|---|---|
| 不开会话 | 47.7、48.9、51.8 | 48.9 |

单次之间差 ±20%（磁盘缓存和先后顺序），中位数之间差不到 1%：开着监控的编译没有可测出的变慢。60.3 秒那次是第二轮的第一次编译（刚还原完）。

内核非分页池的变化（`K32GetPerformanceInfo`）在 −82 MB 到 +140 MB 之间跳，被系统里别的分配淹没，不能用来量会话缓冲区；缓冲区以 `ControlTraceW` 查到的为准。

### 按 D3 判定 2b 的默认模式（初步）

| 条件 | 精确模式的结果 | |
|---|---|---|
| 1. W1：CPU 平均 ≤ 0.5%，工作集增量 ≤ 64 MB | 0.07%，22.3 MB | 通过 |
| 2. W2：丢失 ≤ 0.1%，逐项比对通过 | 丢失 0；存下的原始事件经 Monitor 的解析、重排和汇总回放，16 项全部对上（见下） | 通过 |
| 3. W3：丢失 ≤ 1%，编译变慢 ≤ 10%，单核峰值 ≤ 50% | 丢失 0，中位数快 2%（在误差内），21% | 通过 |
| 4. 会话缓冲区 ≤ 32 MB | 32 MB | 通过 |

结论：精确模式满足 D3 的四条。2a 对话框和设置里的默认记录模式定为"精确"（D2）；2b 常驻服务的默认模式也推荐精确，2b 开始时按服务的实现重新测一次。

### 回放：逐项比对和处理速率（2a.2，普通权限）

`EtwBench replay` 把 W2、W3 存下的原始事件送进 `DiskThinner.Monitor` 的 PayloadParser → ReorderBuffer（W = 1 秒）→ MonitorAggregator，单线程回放 5 遍：

| | W2 写入负载 | W3 编译 |
|---|---|---|
| 事件 | 3,519 | 7,426 |
| 处理速率（单线程） | 约 96,000 个 / 秒 | 约 203,000 个 / 秒 |
| 解析失败 | 0 | 0 |

W2 按 WriteLoad 默认参数逐项比对（新建、删除、重命名个数，写入量，估算增长）：small、big、append（含 FILE_APPEND_DATA 的哨兵偏移、重开追加、cmd 的 `>>`）、temp（关闭时删除）、prealloc（只预分配，估算增长 0）、短路径、move（跨目录移动、整个目录改名）共 16 项全部对上。写入进程都是 `DiskThinner.WriteLoad.exe ← cmd.exe`，cmd 的 `>>` 是 `cmd.exe ← DiskThinner.WriteLoad.exe ← cmd.exe`。

回放中修正了两处：快速 I/O 失败后的 IRP 重试要整个跳过（只扣写入量不够，追加写的哨兵偏移会把估算增长算两遍），快速 I/O 的判断只看 IOFlags 为 0（这类事件的 Irp 字段不是 0）；回放要按第一个进程启动事件把相对时间对齐到真实时间，进程表才能按时间找到实例。

抽样阈值 R 取处理速率较低的一个的一半：每秒 48,000 个写事件（设计 5.3 节）。实测里写事件每秒最多 1,938 个，离这个阈值很远。

## 只能实测确认的问题（V 清单）

| # | 结论 | 对设计的影响 |
|---|---|---|
| V1 | 新建、删除、重命名事件头里的进程号就是发起的进程（W2 里 933 个都是 WriteLoad，5 个是 EtwBench 自己的） | 照设计 |
| V2 | 缓存回写以 System（进程号 4）出现，IOFlags `0x60003`（`IRP_NOCACHE | IRP_PAGING_IO`）；W2 里小文件的回写 18.4 MB。编译时 System 还有 `0x60200` 的写入（复制 .dll/.so/.pdb，34.6 MB），真正写文件的进程看不到。另外发现：缓存写先走快速 I/O（IOFlags 0），失败时再发一个 IRP（`0x60A00`）重试，两个都有写事件，big.bin 的 128 次写入里有 11 次这样重复记了两遍 | 写入量只算 `IOFlags & 0x2 == 0` 的写入（进程号 0 / 4 的非分页写入记到"系统"）；紧挨着的"快速 I/O（IOFlags 0）+ 同一 FileKey、偏移、大小的 IRP 写入"只算一次。进程号 0 / 4 的写入记到"系统（缓存回写或内核）"。估算增长照设计取最大写入位置，记到新建者的进程链（编译时复制出来的文件也能算到 dotnet / MSBuild 名下） |
| V3 | 对不上文件名的写入字节：空闲 71%、编译 33%、写入负载 2.8%。主要是监控开始前就打开的文件（数据库、日志、浏览器缓存） | 第 12.2 节第 7 条的"对不上目录"是常见情况，不是边角；排行里的"对不上目录"一行和"没有能对上这里的写入"的文字照做 |
| V4 | 路径是 `\Device\HarddiskVolumeN\…`；进程映像路径同样；RenamePath 的 FilePath 是新名字（`small\r0.bin`、`move\dst\m0.bin`、目录改名是 `move\done`） | 按"FilePath 是新名字"的规则；旧名字取同一 FileKey 的 NameCreate |
| V5 | 本机：NameCreate / NameDelete v0，Write、DeletePath、RenamePath、CreateNewFile v1，ProcessStart v4，ProcessStop v2。Server 2022 / 2025 等 2a.4 的冒烟测试 | 解析器至少支持这些版本 |
| V6 | 1 MB 缓冲区（实际 44 × 64 KB = 2.75 MB）加回调里每个事件忙等 3 ms，90 秒空闲里丢了 6,261 个（24%）；`TraceEventSession.EventsLost` 和 `ControlTraceW` 查到的 EventsLost 一致，每秒都在涨 | 丢失率照设计按 `EventsLost` 算 |
| V7 | 删掉 `amd64\ x86\ arm64\` 下的原生文件和 `Dia2Lib.dll`、`TraceReloggerLib.dll` 后，开关会话、收事件都正常 | D10：发布包一个都不带（`Directory.Build.targets` 去掉） |
| V9 | 消费进程被强制结束后会话一直在（`Running`），`logman stop <名字> -ets` 能停掉 | 残留清理和兜底任务（D7）都需要 |
| V10 | 覆盖已有文件（`FileMode.Create`）也有 CreateNewFile；目录的 CreateOptions 带 `FILE_DIRECTORY_FILE` | 照设计 |
| V12 | `FileOptions.DeleteOnClose` 建的 50 个文件没有任何 DeletePath；CreateNewFile 的 CreateOptions 带 `0x1000` | 启用第 5.6 节的"关闭时删除"规则 |
| V13 | 通过 8.3 短路径写的文件，事件里的路径是长名字 | 短名换长名只作为兜底，不在热路径上调用 |
| V14 | 只开 `WRITE`（不开 `FILEIO`）就收得到写事件 | 精确模式的关键字 `0x1E10` 照设计 |
| V15 | NameDelete 在改名时对旧名字触发、在名字缓存拆除时大量触发（空闲 3 分钟 99,513 个），删除文件本身不触发；FileKey 没有被复用到别的文件。按 FileKey 存的名字表 3 分钟涨到 8,002 项，没有回落 | 名字表的上限和"延迟建目录节点"必须做（第 12.2 节第 4 条）；按 3 分钟 8,000 项外推，几小时就会到上限，上限按内存实测在 2a.2 定（每项要控制在 100 字节以内） |
| V16 | 只有 `FILE_APPEND_DATA` 的句柄写入时，ByteOffset 是 `0xFFFFFFFFFFFFFFFF`；cmd 的 `>>` 用真实偏移；只 `SetLength` 预分配不产生写事件 | 哨兵值按"写到末尾"处理（估算增长加 IOSize）；预分配的空间估算增长看不到，第 5.6.4 节写明 |
| V17 | 运行中重新 `EnableProvider` 换成轻量关键字，0.5 秒后写的文件已经没有写事件 | D9 的降级可行 |
| V18 | `BufferSizeMB` 是总大小：8 MB → 128 × 64 KB，32 MB → 512 × 64 KB；1 MB 时系统按最少缓冲区数给了 44 个 | 照设计 |
| V19 | 没做（可选）。Kernel-File 清单里没有文件名的 rundown 事件 | 进程列举照设计用 Toolhelp32 |
| V21 | 普通权限下 `TraceEventSession.GetActiveSessionNames()` 能列出所有会话（47 个，含测试会话） | 普通权限下判断"另一个窗口正在监控 / 残留"可行 |
| V22 | 所有负载里事件的时间戳都没有倒序；文件事件也没有早于自己进程的 ProcessStart 到达；空闲时有 6 次写入早于同一文件的 NameCreate 到达（2 秒内） | 重排窗口保留，W 定为 1 秒 |
| V8、V20、V11 | 单文件版、兜底任务的 XML、发布包上的 NuGet 审计警告在 2a.4 核对；本步骤 Release 构建没有 NU 警告 | |

## 存储（2a.3）

`monitor.db`（D4）：会话、按小时的统计、目录（按段存）、映像、进程链、`write_stat`（会话 × 小时 × 目录 × 进程链）。设计 5.8 节的最坏情况合成数据（24 小时，每小时一半的行在 500 个锚点上、一半在新目录上，500 种进程链、300 个映像，计数取上限附近的值）：每小时 1,000 行时一天 2.6 MB（目标 ≤ 4 MB），每小时 2,000 行时 4.5 MB（目标 ≤ 8 MB）。保留按开始时间删整个会话，按实际占用的页（不是文件大小）判断，超出上限时只删需要删的那几个。
