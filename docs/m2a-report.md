可清理 36.0 GB 的构成：安全 25.4 GB，需重新下载 9.89 GB，丢历史或登录态 0.72 GB。最大的几项：用户 Temp 6.17 GB、ASP.NET 临时文件 5.99 GB、Chromium/Electron 缓存（252 处）4.53 GB、NuGet 全局包 4.02 GB、内核实时转储 2.93 GB、npm 缓存 2.90 GB。

和阶段 0 的覆盖率实验（用户目录 90.7%、可清理 39.1 GB）相比，解释率略高，可清理略少。原因是正式规则收紧了"可清理"的口径（见下）。

## 安全上的几个决定

- 不收"所有 `*.log` 文件"这条通用规则。Chromium/Electron 的 LevelDB（Local Storage、IndexedDB）和 ESE 数据库（Windows Search、WebCache）都用 `.log` 做事务日志，删了会损坏数据。只认名为 `log` / `logs` 的目录，并有测试覆盖 `Local Storage\leveldb\000003.log` 不可清理。
- 只有"可执行"的规则才计入可清理：必须是 `dir` / `file` 规则，并且有 `delete` 或白名单命令动作。兜底规则（`under`）和只有说明的规则（比如"在扩展面板里卸载""删除旧版本"）只解释"这是什么"，不算清理建议。因此 Codex 的旧组件、Claude Code 的旧版本、Playwright 浏览器这些"需要先判断哪个是旧版本"的位置，不计入 36 GB。
- 和别处用硬链接共享的文件不计入可清理（删了不释放空间）。
- 规则校验在写规则时拦截：可清理规则落在保护名单或"只能用系统工具处理"的位置会报错；凭据必须是 never；safe/low 必须有依据；草稿不能是 safe，也不能有命令动作；命令只能引用白名单编号；路径必须以令牌开头，不能有 `..`，`**` 最多一次。

截图检查了 100% 和 150% 缩放、遍历和 MFT 两种扫描（`artifacts/m2/`、`artifacts/m2/elevated/`）。

- 概览页（新）：已用空间（带进度条）、可释放（按风险拆分）、未识别（含超过 100 MB 的块数）三张卡片，"近 7 天净增长"留到 M3。"建议先处理"按规则汇总可清理空间，加上只能用系统工具处理的大项（WinSxS、Installer）和最大的未识别位置；"占用最多"把规则位置和未识别位置混排。双击或回车跳到空间浏览并选中。

## 未完成和问题

- 主程序峰值内存：这次在 150% 缩放、加载规则后是 343 MB；M1 在 100% 缩放、无规则时是 281 MB。两次条件不同，不能直接比较，但已超过 300 MB 的目标。规则匹配本身的数组约 30 MB，其余要在 M2 下半用同样条件重测后再定位。
- 归属：通用结构规则（如 Chromium 缓存）还不知道属于哪个软件，归属列为空；M2 下半用已装软件和目录名推断，标"推断"。
- "按归属汇总""按类别汇总"视图在 M2 下半实现。
- 42 条规则在这台机器上没有命中（uv 之外的语言工具链、Docker/WSL、JetBrains 等），需要在装了这些工具的机器上实测。
- 还没解释的大块：`jstclient` 的本地向量模型（1.21 GB `.onnx`）、`C:\ProgramData` 的零散部分、搜狗输入法数据、`~\.local\bin\claude.exe` 和 `.orig` 备份，可以补进下一批规则。
