## 0.2 MFT 扫描与遍历扫描

两种扫描都以管理员身份在同一时段运行（`ScanBench all C:`）。

| 指标 | 遍历扫描 | MFT 扫描 | 目标 |
|---|---|---|---|
| 总耗时 | 86.8 秒（普通权限 118 秒） | 4.7 秒（冷缓存 6.1 秒，热缓存 3.5 秒） | ≤ 10 秒 |
| 文件 / 目录 | 699,915 / 322,079 | 700,147 / 322,133 | |
| 占用汇总 | 163.8 GB | 144.7 GB | 卷已用 147.2 GB |
| 扫描后常驻内存（回收后工作集） | 152 MB | 161 MB | ≤ 300 MB |
| 峰值内存 | 376 MB | 416 MB | 见下方"待改进" |
| 树结构本身 | 118 MB | 118 MB | |

一致性：只比较遍历扫描能完整列出的顶层目录，文件数 420,767 对 420,773（差 6 个），逻辑大小差 98 MB（0.11%）。

差异来源都已查明：

- 遍历扫描拿到的是目录项里缓存的大小，正在写入的文件会偏小。实例：`C:\ProgramData\ASUS\…\ASUS_System_Control_Interface.etl`，目录项显示 0.8 MB，实际 383.7 MB。MFT 读的是文件本身的记录，没有这个问题。
- 硬链接：C 盘有 118,287 个附加硬链接名（主要是 WinSxS 和 System32 之间）。遍历扫描每个名字都按完整大小算，所以占用汇总（163.8 GB）超过了卷已用空间。MFT 只算一次。
- System Volume Information 即使管理员也列不出内容，MFT 能看到 3.09 GB。
- MFT 汇总比卷已用空间少 2.5 GB（1.7%），其中 0.5 GB 是目录索引（没有计入树）。WizTree 自己在 10-19 的导出里也有约 2.1% 的同类差距。

验证中发现并修复的问题：第一次 MFT 扫描的占用汇总是 344.7 GB，原因是 `$BadClus:$Bad` 这类稀疏流的属性头声称分配了整个卷的大小。改为按数据段统计实际分配的簇数后正确，并补了稀疏流、压缩文件、跨扩展记录的分段流三个测试。

遍历扫描的速度：瓶颈在文件系统本身（含杀毒等过滤驱动），不在我们的代码。在用户目录（27 万文件）上测：

| 方式 | 耗时 |
|---|---|
| `dir /s` | 64.5 秒 |
| .NET 单线程递归枚举 | 17.5 秒 |
| WalkScanner 4 / 8 / 16 线程 | 14.5 / 15.5–17.1 / 12.1 秒 |

默认线程数改为最多 16。整个 C 盘普通权限仍需约 2 分钟，所以界面上必须有进度和取消，并且明显地建议"以管理员身份重启"。

## 0.3 界面性能

模拟数据 130 万节点，另用真实用户目录（36.7 万节点）对照。窗口 1440×900，方块图区域 1148×246。

| 操作 | 模拟 130 万 | 真实 36.7 万 |
|---|---|---|
| 全部展开（可见行数 = 节点数） | 221 毫秒 | 82 毫秒 |
| 连续翻页重绘，平均 / p95 | 0.8 / 3.5 毫秒 | 0.6 / 1.4 毫秒 |
| 随机跳转重绘，平均 / p95 | 28 / 58 毫秒 | 28 / 47 毫秒 |
| 折叠根目录 / 再展开 | 11 / 186 毫秒 | 10 / 81 毫秒 |
| 方块图布局 / 绘制 | 2.4 / 18.8 毫秒（8,141 块） | 1.8 / 14.5 毫秒（4,216 块） |
| 方块图点击定位到列表 | 3.0 毫秒 | 1.6 毫秒 |
| 常驻内存 | 265 MB | 214 MB |

截图检查发现方块图里没再细分的目录没有填色，整片看起来像灰色噪点；已改为整块填色，并且小于 6 像素的块不画边框。真实数据截图看起来正常。

结论：虚拟模式 ListView 加 GDI 自绘方块图足够，不需要第三方控件。

## 0.4 规则覆盖率

数据：`.kiro\scan\c_drive.csv`（WizTree 10-19 14:22 导出，107 万个节点）。候选规则 135 条，在 `spikes/RuleCoverage/candidate-rules.txt`。按分配大小统计。

| 规则层 | 累计规则数 | 用户目录解释率 | 用户目录可清理 | 整个 C 盘解释率 | C 盘可清理 |
|---|---|---|---|---|---|
| 只有系统位置 | 33 | 12.3% | 0 | 71.4% | 18.5 GB |
| + 通用结构规则 | 64 | 56.6% | 24.0 GB | 84.8% | 43.7 GB |
| + 开发与 AI 工具 | 126 | **90.7%** | **39.1 GB** | 94.7% | 58.8 GB |
| + 常用软件抽样（9 条） | 135 | 95.5% | 39.7 GB | 96.1% | 59.3 GB |

用户目录共 58.1 GB。"解释"包括"不能删"的用户数据和程序文件；"可清理"指风险为安全、需重新下载、丢历史或登录态的部分。另有 49.4 GB 只能交给系统工具处理（WinSxS、pagefile 等）。

数据上的一个限制：WizTree 的文件行里，硬链接每个名字都带完整大小，所以从文件汇总的 C 盘总量（200.8 GB）比 WizTree 自己的根目录统计（180.8 GB）多 20 GB，多出的部分基本在 Windows 目录。用户目录几乎没有硬链接，那一栏的数字可靠。

命中空间最多的通用规则：用户 Temp（8.97 GB）、系统服务 Temp（8.63 GB）、ASP.NET 临时文件（6.04 GB）、Chromium/Electron 缓存（3.95 GB）、Service Worker 缓存（2.66 GB）、带 `CACHEDIR.TAG` 的目录（1.76 GB）、日志目录（1.55 GB）。

还没解释的大块（热点分解，阈值 200 MB），作为 M2 补规则的候选：

| 位置 | 大小 | 建议 |
|---|---|---|
| `C:\Recovery\Customizations\usmt.ppkg` | 3.16 GB | 系统位置：OEM 恢复配置，只给引导 |
| `C:\ProgramData\Downloaded Installations` | 410 MB | 安装程序缓存 |
| `C:\ProgramData\SogouInput` | 382 MB | 应用规则 |
| `%LOCALAPPDATA%\antigravity-updater`、`%LOCALAPPDATA%\@deepseek-aidsh-desktop-updater\installer.exe` | 590 MB | 通用规则：Electron 自动更新器下载的安装包（`*-updater` 目录） |
| `%LOCALAPPDATA%\Microsoft\Terminal Server Client\Cache` | 247 MB | 系统位置：远程桌面位图缓存，安全 |
| `%LOCALAPPDATA%\Microsoft\OneNote\16.0\备份` | 217 MB | 应用规则：用户数据 |

有 42 条规则在这台机器上没有命中（uv、pnpm、Gradle、Cargo、Docker、WSL、JetBrains 等没装或已清理）。它们保留在第一批里，但在有这些工具的机器上实测之前标为草稿。

M2 第一批规则：上表前三层的 126 条，加上热点里的 5 到 6 条，约 130 条。

## 0.5 Native AOT

- Core 和 Scanner 开启了 `IsAotCompatible`，没有任何裁剪或 AOT 警告。用 AOT 发布的 ScanBench 只有 2.36 MB，扫描 `.nuget`（2.5 万个文件）峰值内存 31 MB，JIT 版本是 53 MB。阶段 2b 的常驻服务可以放心用 AOT。
- WinForms 主程序用 AOT 发布直接报 NETSDK1175（不支持裁剪），社区方案没有尝试。主程序保持 JIT。
- 主程序发布体积：依赖运行库版共 0.21 MB（需要 .NET 10 桌面运行库），自包含单文件压缩版 47 MB。

## 对研发方案的调整

1. 遍历扫描改用 .NET 的 `FileSystemEnumerable`（底层是 `NtQueryDirectoryFile`），不直接调 `FindFirstFileExW`，效果相同，代码更简单。
2. 遍历模式的三个局限要在界面上说明：正在写入的文件大小可能偏小、硬链接重复计算、占用是估算值。状态栏显示"遍历扫描（估算）"，并提供"以管理员身份重启"。
3. M1 增加一项：降低 MFT 扫描的峰值内存（目前约 416 MB，目标 ≤ 300 MB）。思路：解析时直接写节点数组，不再经过按记录号的中间数组；名称池按实际用量预估。
4. M2 的第一批规则按 0.4 的结果定为约 130 条。
