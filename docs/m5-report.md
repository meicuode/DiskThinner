## 设置

`%LOCALAPPDATA%\DiskThinner\settings.json`，System.Text.Json 源生成。读不了或格式不对时用默认值，坏文件改名为 `settings.json.bad-时间` 留着，不删除；手改出来的越界值收回到界面能选的值。写入时先写临时文件再替换。

| 设置 | 默认 | 生效 |
|---|---|---|
| 每日快照、时间 | 关、12:00 | 立即注册或移除计划任务（和增长分析页的按钮是同一个任务） |
| 扫描后自动保存 | 开 | 下次扫描 |
| 只记录大于 | 50 MB 的目录（可选 20 / 50 / 100 / 200） | 下次保存快照；snapshot 子命令也读这个设置 |
| 保留 | 180 天（可选 90 / 180 / 365） | 下次保存快照 |
| 临时文件 | 只删 24 小时前的（可选 7 天） | 立即重新生成计划。只对本来就带时间条件的临时文件规则生效，取规则和设置里更严格的那个；执行前复核拒绝比规则宽松的条件 |
| 被占用的文件 | 跳过并记录（可选询问是否关闭程序） | 确认框里那个选项的默认值 |
| 我的保护目录 | 无 | 执行清理时立即生效（计划是在添加之前生成的也一样）；规则引擎重新加载后，下次扫描的计划和风险标签也会更新。可以是任意本地盘上的目录，不能含通配符，不能是整个盘 |

"查看内置保护名单"列出全部内置项、级别和原因；内置项不能删除。

## 日志和异常

- `logs\app.log`：启动、扫描完成、清理开始和结束、设置更新、每日快照开关；超过 512 KB 只保留后一半。`snapshot.log` 用同一套写法。
- 界面线程上未处理的异常：写日志和一份 `crash-时间.txt`（版本、系统、完整异常），提示后程序继续运行。其他线程和未等待任务的异常也写崩溃报告。日志只在本机。

## 打包

`tools/release/build-release.ps1` 生成两个 zip 和 `SHA256SUMS.txt`，都放在 `artifacts\release\<版本>\`；目标目录已经存在时直接报错，不覆盖已有的发布文件。版本号 0.1.0 来自 `Directory.Build.props`，产品版本里带构建时的提交号。

单文件自包含版不开启单文件压缩。实测压缩后 exe 48.5 MB、zip 43.3 MB，不压缩 exe 105.6 MB、zip 44.5 MB，下载只差 1 MB 左右；但压缩版启动时要把程序集解压到内存，同样扫描一个小文件夹，峰值工作集 193 MB 对 87 MB，MFT 扫描整个盘时会超过 300 MB 的目标。WinForms 不支持裁剪，所以自包含版体积主要是运行库本身。

## 内存

管理员下用两个发布包扫描 C 盘，峰值工作集 316 MB 和 317 MB，比 M4 的 264 MB 多约 50 MB，而且多出来的部分在扫描开始之前就有了（扫描前 117 MB，M4 是 64 MB）。排查结果：这台机器装了搜狗输入法，窗口获得键盘焦点后会往进程里注入 5 个 DLL（`ichat_bundle64.dll`、`isgpet_bundle64.dll` 等），工作集多出约 50 MB、私有内存多出约 34 MB；M4 测量那次窗口没有拿到焦点，没有注入。用 M4 的提交单独构建一份做对比，在没有注入的情况下扫描同一个小文件夹，M4 和现在的峰值分别是 79 MB 和 81 MB，有注入时都在 129–139 MB。所以程序自己的内存和 M4 基本一致；在装了这类输入法的机器上，峰值会比 300 MB 的目标高。

## CI 和自动发布

- `.github/workflows/ci.yml`：windows-latest 上规则校验、Release 构建、全部单元测试。推到 GitHub 后第一次运行（提交 `f1f930d`）通过。CI 里没有交互会话，账户检查的测试放宽为"查不到会话用户时不算不一致"。
- `.github/workflows/release.yml`（M5 之后补充）：推送 `v*.*.*` 标签时检查标签格式、规则校验、构建、测试，用打包脚本打两个 zip（版本号以标签为准，和 `Directory.Build.props` 不一致时给警告），上传构建产物，创建 GitHub Release 并附上两个 zip 和 `SHA256SUMS.txt`；带 `-` 后缀的版本发布为预发布；同一个标签重新运行时替换附件。本地演练了标签解析（合法、预发布、缺修订号、含分号四种）、发布说明生成（有和没有说明文件两种）、打包脚本的 `-Version` 参数，各步骤的 PowerShell 都能解析，YAML 用 pyyaml 校验通过。
- `.github/workflows/package.yml`：打包后在全新的 windows-2022 和 windows-2025 上运行 `tools/verify/smoke.ps1`，CI（推送到 main）和发布都会调用；发布要等冒烟测试通过。第一次运行时打包失败，暴露了一个本机没发现的问题：`dotnet publish -r win-x64` 把 RuntimeIdentifier 传给了规则编译工具 dtrule，它输出到 `win-x64` 子目录，干净的机器上主程序找不到它。本机一直有早先构建留下的 dtrule.dll，所以没暴露。修正后在新克隆的仓库里验证，CI 全部通过（提交 `abf1d13`）：

| 机器 | 自包含版：MFT 扫描 C 盘 | 峰值 | 清理计划 | 快照 |
|---|---|---|---|---|
| windows-2022 | 1,783,411 项，15.6 秒 | 366 MB | 27 项，默认勾选 20 项，预计释放 1,285 MB | 192 KB |
| windows-2025 | 1,403,124 项，9.8 秒 | 323 MB | 15 项，默认勾选 11 项，预计释放 1,266 MB | 128 KB |

两台机器上依赖运行库的版本（装好 .NET 10 之后）和自包含版扫描测试文件夹、snapshot 子命令都正常，没有崩溃报告。

第一次推送 `v0.1.0` 标签（指向 `d75fb34`）时，Release 工作流在测试这一步失败（147 秒，CI 同一提交 25 秒），没有发布任何东西。排查中发现运行官方命令时可能无限等待：命令留下的后台子进程（npm 的更新检查等）拿着输出管道时，会一直等到子进程结束。改为进程退出后等输出读到结尾、最多 5 秒（`72d7129`、`f6b5543`），并让 CI 和发布在测试失败时把失败的用例写成注解。标签移到 `f6b5543` 后重新发布成功。日志需要管理员权限才能下载，第一次失败具体是哪个用例没能确认。CI 机器的 C 盘比开发机多 35% 到 70% 的文件，峰值内存按文件数增长（开发机约 104 万项时 264 MB），超过了 300 MB 的目标；MFT 扫描 15.6 秒也超过了 10 秒的目标（虚拟机磁盘较慢）。

## 干净虚拟机上的验收步骤（待做）

在全新安装的 Windows 10 22H2 和 Windows 11 24H2 虚拟机上各走一遍：

1. 解压单文件自包含版，双击运行：普通权限下扫描 C 盘，概览、空间浏览、增长分析、清理计划、操作记录、设置都能打开。
2. 点"以管理员身份重启"，确认 MFT 扫描几秒完成。
3. 在清理计划里只勾选"当前用户的临时文件"执行一次，核对确认框、进度、操作记录和实际释放。
4. 设置里开启每日快照，确认计划任务注册成功，手动运行一次任务后增长分析里多一个快照；再关闭。
5. 解压依赖运行库的版本：没装 .NET 10 桌面运行库时双击应提示下载；装上后能运行。
